# 业主清册导入增强 — 需求规格（INCREMENTAL）

## 执行摘要

业务背景（用户 2026-11-10 原话）："管理员业主清册导入，批量导入支持哪些文件，是否有格式要求。能否在页面有一个模板下载？ 这个模板要灵活，因为一个专有部分可能登记多个产权业主，可能一个，两个，三个，特别的可能五六个甚至更多。数量上不应该受限。单个导入，或者批量导入，都应该记录专有部分类型，比如住宅，公寓，商铺，车位，专有部分面积等等。"用户要求先整理需求和用户故事，确认后再开发。

本版（0.3.0）依据用户对 Q-RI-13 ~ Q-RI-22 的答复修订，答复原话（2026-11-10）："Q-RI-18=B，Q-RI-22 上限 60 秒，其他按推荐"。映射：Q-RI-13=A、14=A、15=A、16=A、17=A、18=B、19=A、20=A、21=A、22=A（同步等待，20000 行处理上限 60 秒）。0.2.0 中按推荐项暂定的取值现全部转为"已确认"；各条变更在对应需求"备注"中以"变更前 → 变更后"标出。

- 功能需求 16 条（REQ-FUNC-083 ~ 098）/ 非功能需求 5 条（REQ-NFUNC-011 ~ 015，其中 015 为 0.3.0 新增）。编号接续基线（基线最大 REQ-FUNC-082、REQ-NFUNC-010、C-20、US-091）。
- `[INFERRED]` 0 条，占比 0 ÷ (16 + 5) = 0%，不超过画像 `inferred_max` 20%。0.2.0 中唯一的 INFERRED（REQ-FUNC-090 姓名必填）已由 Q-RI-13=A 确认，转为有来源。
- 优先级规则：用户信号照用；用户明确提到的功能为 Must Have，其余为 Should Have。按此规则：FUNC Must Have 14 条（083 ~ 092、095 ~ 098），Should Have 2 条（093、094）；NFUNC 5 条均为 Must Have。
- 用户答复"其他按照推荐"：0.2.0 阶段的 Q-RI-01=A、03=A、05=B、07=A、08=A、09=A、12=A 与本版的 Q-RI-13 ~ 17、19 ~ 21 均按推荐项确认（见"已确认问题"）。
- 开放问题：无阻断项。仅剩非阻断的 Q-RI-23（60 秒的计量环境与口径，已按默认值写入 AC，用户可改）。
- 本次只做需求与用户故事；不含技术实现。

### 变更影响分析

| # | 影响 | 结论 | 依据 |
|---|---|---|---|
| 1 | 手机号选填后，没有手机号的产权人无法走"手机号与清册一致即认证"（REQ-FUNC-011） | 现有认证只比对"用户已验证手机号是否在该专有部分的清册手机号中"，姓名不参与（C-21）。没有登记手机号的产权人只能走产权申诉（REQ-FUNC-019）由管理员审核；REQ-FUNC-098 要求页面给出该指引 | `backend/apps/residency/views.py:44-50`；`backend/apps/registry/services.py:7-8` |
| 2 | "注册并认证成功后自动绑定"与现有流程的关系 | 自动绑定是 REQ-FUNC-011 的第二个触发入口：现有入口是"用户逐级选择专有部分后点击认证"，新入口是"用户已验证的手机号命中清册时系统代为认证"。触发时机已确认（Q-RI-18=B）：用该手机号注册并验证成功时，以及已注册用户（含微信用户）首次验证并绑定该手机号时；清册后补不触发。手动流程保留，用于自动绑定未覆盖的情形（如手机号登记晚于注册）。一号多户全部绑定、先到先得为户主、用户端提示与审计见 Q-RI-19 ~ 21（均为 A） | `residency/views.py:51`、`backend/apps/residency/services.py:14-42`；`backend/apps/accounts/services.py:168-185`；基线 REQ-FUNC-010/011/013 |
| 3 | 用户端显示面积是否触及 REQ-NFUNC-002（手机号脱敏） | 面积是房屋属性、不是个人信息，不适用手机号脱敏规则；姓名、手机号仍只在管理员维护清册时可见，选择专有部分及自动绑定的任何提示都不得带出他人姓名或手机号 | 基线 REQ-NFUNC-002（`project_workspace/ocap/requirements/requirements_spec.md:222`）；`frontend/src/portal/Units.vue:5`、`:16-18` |

| 5 | 20000 行同步处理的时长 | 已确认（Q-RI-22=A）：同步等待并显示处理中，20000 行处理上限 60 秒，写入 REQ-NFUNC-015 | 用户原话 "Q-RI-22 上限 60 秒" |

## 约束

接续基线 C-20，本次新增：

- C-21：认证仍只比对手机号（REQ-FUNC-011），本次新增的类型、面积、姓名不改变认证与身份规则。来源：基线 REQ-FUNC-011；本项目范围。
- C-22：清册手机号被修改或删除后，已认证身份保留（REQ-FUNC-033）；导入或编辑移除业主不得撤销任何已认证身份。来源：基线 REQ-FUNC-033。
- C-23：不收集证件号码、银行卡号等敏感个人信息（如需，须另行评审）。来源：协议 §L-2；Q-RI-02 推荐项。
- C-24：现有手机号规则（11 位、同一专有部分内唯一、同一手机号可出现在多个专有部分）继续有效；同一专有部分内不同姓名使用同一手机号的行失败（Q-RI-17=A 确认）。来源：`backend/apps/registry/models.py:25-32`、`views.py:105`；`"其他按推荐"`。
- C-25：自动绑定只能由"已通过验证的手机号"触发，未验证的手机号不得触发；自动绑定不绕过现有认证规则（已是产权业主不重复、同住人升级为产权业主、户主规则）。来源：用户原话"认证成功"；基线 REQ-FUNC-011；`residency/services.py:14-42`。
- C-26：自动绑定仅在 REQ-FUNC-096 规定的两个时机触发；管理员事后新增、导入或修改清册手机号，不得使任何已存在的用户自动获得产权业主身份。来源：`"Q-RI-18=B"`（选项 C 已评估未采纳）。
