# CI/CD 流水线：房屋选择结构整理、申诉审核增强、认证姓名核对与席位授予放宽

## 现状与影响

现有 CI：`.github/workflows/ci.yml`（GitHub Actions，push/PR 到 main，只测试与构建，不部署，画像 P7）。
- `backend`：Python 3.13，`manage.py check` + 全量 Django 测试（`config.test_settings`，SQLite 内存库，`MIGRATION_MODULES` 置空）。
- `frontend`：Node 20，`npm ci`，主题定义校验，vitest，生产构建（`--base=/ocap/`）。
- `miniprogram`：Node 20，`npm install --legacy-peer-deps`，vitest。

本次改动对 CI 的影响（依据 module_design「数据迁移」「受影响的运行单元」、implementation_plan、e2e_test_report 全量回归表）：
- 新增测试由现有 job 自动收集：后端 822（基线含 1 条已修正的环境失败）-> 945（全 OK）；前端 259 -> 281；小程序 97 -> 104（e2e_test_report「全量回归」）。
- **有 1 个新迁移** `residency/migrations/0003_appeal_owner_name.py`（手写、可逆）。CI 的测试库置空 `MIGRATION_MODULES`，**迁移不会被 CI 跑到**；因此迁移的前向/反向只在 GROUP_C 的 scratch SQLite 上验证过（implementation_plan「迁移」），真实 MySQL 上的首次执行是部署阶段 A 的 DEPLOY-004。这是已知缺口，缓解：阶段 A 先 mysqldump `residency_appeal`、先 `migrate --plan` 核对只含 0003、回滚含 `migrate residency 0002`。
- 无新依赖（`git diff --name-only 15ea79e c32684b -- backend/requirements.txt frontend/package.json frontend/package-lock.json miniprogram/package.json` 无输出）、无新环境变量、无新服务；新增管理命令 `relocate_shops` 随代码入库，CI 只经 SQLite 测试库覆盖，**不在 CI 中执行任何真实数据操作**。
- `backend/tests/remote/**` 不被默认测试命令收集（画像 P4-1），CI 不运行；其 TC-E2E-337 已改为只提交/驳回并带护栏。
- 小程序：CI 只跑 vitest，**不构建、不发布**。`uni build -p mp-weixin` 在开发机不可用（既有工具链问题），小程序构建与发布由用户在 HBuilderX/微信开发者工具完成，不在画像 P7 范围内（见 deployment_plan「小程序发布顺序」）。
- 待部署提交 `c32684b`（本地，**未推送**；其父 `68bc477` 亦未推送）。未推送时 GitHub CI 不会运行本批提交；部署前的测试证据以 GR-D-001 的 PM 复跑为准 [INFERRED: 建议用户同意推送后确认 GitHub CI 通过；推送由用户另行决定，画像 P9]。
- CI 仍使用 `--passWithNoTests`（画像 P4 写法）：本批前端与小程序均有用例，缺口不适用。

**无需修改 CI 配置**（`ci.yml` 不动）。理由：全部新增测试自动被收集；新增命令与迁移不需要 CI 步骤；小程序构建属画像外手工流程。

## 流水线概览

[Source] -> [后端 check + 全量测试] -> [前端 主题校验 + vitest + build] -> [小程序 vitest] -> [迁移漂移与新增文件核对（开发机）] -> [Package（开发机，授权后）] -> [Deploy 测试环境 阶段 A，须授权] -> [Smoke] -> [数据操作 阶段 B~D，各自独立授权，非自动阶段] -> [部署后验证与远程 E2E 阶段 E，须授权] -> [小程序构建与发布（用户手工，画像外）]

数据操作（relocate_shops dry-run、apply、导出）**不是 CI/CD 自动阶段**，永远不进入自动化触发（ADR-107：不做成迁移，避免被 `migrate --noinput` 自动执行）。

## 阶段定义

| PIPE | 阶段 | 触发条件 | 命令 | 成功标准 | 失败处理 |
|---|---|---|---|---|---|
| PIPE-01 | Source | push / PR 到 main | `actions/checkout@v4` | 检出成功 | abort-and-notify |
| PIPE-02 | 后端检查与测试 | 同上 | `cd backend && python manage.py check --settings=config.test_settings`；`python manage.py test --settings=config.test_settings -v 2` | 退出码 0；945 项 OK，无新增失败 | abort-and-notify，不部署 |
| PIPE-03 | 前端校验、测试与构建 | 同上 | `node scripts/themes/build.mjs --strict --check`；`npx vitest run --passWithNoTests`；`VITE_API_BASE=/ocap/api/v1 npm run build -- --base=/ocap/` | 主题 check 通过；281 项通过；构建退出码 0 | abort-and-notify |
| PIPE-04 | 小程序测试 | 同上 | `npx vitest run --passWithNoTests` | 104 项通过 | abort-and-notify |
| PIPE-05 | 迁移漂移与迁移文件核对（开发机，部署前，M-DE-002） | 部署授权前 | `cd backend && <Django 5.2.x venv>/bin/python manage.py makemigrations --check --dry-run --settings=config.test_settings`；`git show c32684b:backend/apps/residency/migrations/0003_appeal_owner_name.py \| grep -c "Generated by Django"` | 退出码 0（若报告与本批无关 app 的既有漂移，须在基线提交 15ea79e 的干净检出（`git worktree` 临时目录）中确认同样存在，并只确认 residency 无漂移）；`grep -c` 输出 `0`（手写，画像 P6）。不用 Django 6.x | 非 0 或出现 residency 漂移即停止，交回开发（不得在目标机生成迁移，P8） |
| PIPE-06 | 制品打包（开发机，阶段 A 授权后） | 用户当轮授权阶段 A | 后端：`git archive --format=tar.gz c32684b:backend`（只含已提交跟踪文件，M-DE-012）；前端：在工作树构建 `frontend/dist`（要求 `git diff --quiet c32684b -- frontend` 且 `frontend/` 无未跟踪文件）；两包 SHA256 记录并与目标机比对 | 包生成、SHA256 两端一致 | abort-and-notify |
| PIPE-07 | 部署（测试环境，阶段 A） | 用户当轮授权阶段 A | deployment_plan DEPLOY-001~006（含 mysqldump `residency_appeal`、`migrate`） | 全部 DEPLOY 完成、验证通过 | 逆序 ROLLBACK（**不得跳过失败继续部署**）；回滚含 `migrate residency 0002` 且在恢复旧代码之前 |
| PIPE-08 | 部署后冒烟（阶段 A 末） | PIPE-07 成功后 | deployment_plan「阶段 A 部署后验证」 | 全部检查通过 | 失败即报告，由用户决定回滚；至多对「建连」重试（显式成功标记，M-DE-009） |
| PIPE-09 | 数据操作（阶段 B/C/D） | 各阶段用户当轮独立授权，上一阶段结果已汇报并获用户确认 | deployment_plan DEPLOY-007~012 | 各阶段成功标准（B：would_change=107 且 conflicts=0） | abort-and-notify；不自动重试写操作；B 结果不符立即停止汇报 |
| PIPE-10 | 远程 HTTP E2E（阶段 E） | 用户当轮授权阶段 E | 画像 P4-1：`e2e_` 夹具 setup -> `backend/tests/remote/run_remote.py` -> 夹具 cleanup | 套件无本批新增失败；清理后清册计数与基线相同；护栏拒绝一切“通过申诉” | abort-and-notify；失败仍须执行 cleanup |
| PIPE-11 | 小程序构建与发布（用户手工，画像外） | 用户自行决定（建议顺序见 deployment_plan） | HBuilderX/微信开发者工具构建、提交审核、发布 | 新版可用；旧版认证/申诉得 400 的过渡期可控 | 用户自行处理；不在子代理范围 |

触发说明：PIPE-01~05 为自动/开发机阶段；PIPE-06 起全部为手动，每个授权点见 deployment_plan「授权点总表」。CI 只跑测试与构建，不部署（画像 P7）。

## 制品管理

- 存储位置：开发机本地 `mktemp -d` 临时目录（后端包、前端包）+ 目标机 `/home/yangyang/ocap/snapshots`（回滚快照、数据备份）。
- 命名：后端 `backend-<TS>.tar.gz`、前端 `web-<TS>.tar.gz`、nginx `*.bak_<TS>`；数据备份 `residency_appeal-<TS>.sql`（迁移前）、`ocapdb-registry-<TS2>.sql`、`shops-<TS2>.jsonl`；`TS`/`TS2` 为 `YYYYMMDDHHMMSS`。导出文件由命令自动命名 `registry_import_YYYYMMDD-HHMMSS.xlsx`。
- 版本标识：部署版本 = 本地 main 提交 `c32684b380e0e3cbce66e93bb58acb5972c750b1`（未推送）；包 SHA256 在两端比对并记入报告（M-DE-006：目标机无 git）。上一次已部署提交 = `15ea79ea51c87d56cd1cd8113cba81007649575a`（回滚基线，已在 origin/main）。

- 无制品库；风险：制品不可追溯，靠锚点 TS、提交号与 tar SHA256 定位（已知缺口，沿用 ocap-deploy §9）。
- 含个人信息的文件（`ocapdb-registry-*.sql`、导出 xlsx）：不是制品，不入库、不上传到其他位置，仅存目标机（0600，位于 700 目录或 `snapshots/`）。上批遗留的 `snapshots/ocapdb-registry-20261116134900.sql`、`snapshots/underground-20261116134900.jsonl` 用户要求保留到 2026-11-23，**本流水线任何步骤不得删除**。
