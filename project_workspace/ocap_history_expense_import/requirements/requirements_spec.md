# 历史支出批量导入 — 需求规格（增量）

## 执行摘要

- 业务背景：用户要在 ocap 中导入 `2022Q3～2026Q3` 的过去几年历史支出，逐笔保留明细，并据此生成往年季度/年度报表；当前系统只有收入表支持批量导入，支出只能逐笔走报销/备用金审批。用户已选择“方案A：新增历史支出批量导入”，原话：“Use Skill: sdlc-orchestrator 走方案A， 开始吧”。
- 数量：功能需求 9 条（REQ-FUNC-342~350）/ 非功能需求 1 条（REQ-NFUNC-073）；INFERRED 2 条，2 ÷ (9 + 1) = 20.0%，等于画像上限 20%。
- 优先级默认规则（按本技能规则 3）：用户明确要求的功能为 Must Have，其余为 Should Have。Must Have 7 条，Should Have 2 条；非功能 1 条为 Should Have。

## 现有系统基线（INCREMENTAL）

| 现有能力 | 位置 | 与本需求的关系 |
|---|---|---|

## 功能需求

| ID | 描述（系统应当…） | 来源 | 优先级 | 增量类型 | 备注 |
|---|---|---|---|---|---|
| REQ-FUNC-342 | 系统应当允许有权限的用户下载“历史支出导入模板”，模板列固定为：日期、金额、支出类别、用途/事由、备注；同时支持 xlsx 与 CSV 两种格式 | 用户要求“新增导入模板、后端接口、前端入口”（方案A 接受） | Must Have | 新增 | 模板列与导入校验共用同一份列定义；xlsx 可含“填写说明”工作表 |
| REQ-FUNC-343 | 系统应当提供“历史支出批量导入”入口，允许上传 xlsx 或 CSV 文件；只读取第一个工作表；文件 ≤5MB、数据行 ≤5000 行 | 用户要求“过去几年的历史支出”批量导入（方案A） | Must Have | 新增 | 日期不得晚于导入当天 |
| REQ-FUNC-344 | 系统应当逐行校验导入数据：日期必填且可解析、不得晚于今天；金额必填、大于 0、最多两位小数且不超过系统金额上限；支出类别 ≤32 字；用途/事由 ≤200 字；备注 ≤200 字；错误行跳过并提示行号与原因，其余有效行照常导入；若全部行无效则不创建导入批次 | 方案A：“导入前预览/校验错误行、跳过错误行并提示行号” | Must Have | 新增 | 与收入表导入的错误行处理口径保持一致 |
| REQ-FUNC-345 | 系统应当在导入时判定重复行：日期、金额、支出类别、用途/事由四项完全相同，且与已有有效历史支出（或同批次文件内）重复时，该行跳过并提示行号；四项任一项不同则不视为重复 | 方案A：“跳过重复或错误行并提示行号” | Must Have | 新增 | 重复行不计入成功行；全部重复/错误同样不创建批次 |
| REQ-FUNC-346 | 系统应当把通过校验的历史支出逐笔写入台账，方向为支出，日期取“日期”列，金额取“金额”列，类别与用途进入台账摘要；记录须标记为“历史导入”并关联导入批次；不得创建报销/备用金/核销申请，不得创建审批实例，不得进入审批待办 | 方案A：“直接写入台账、标记历史导入、保留审计、不再逐笔审批” | Must Have | 新增 | 这是对现有“支出必经审批”的业务例外，理由与风险见 C-377、C-378 |
| REQ-FUNC-347 | 系统应当提供历史支出导入批次列表与明细查看：批次时间、操作人、文件名、总行数、成功行数、跳过/失败行数、金额合计、状态；明细可查看每行日期、金额、支出类别、用途、备注与处理结果 | 方案A 的可追溯与“保留操作人/时间/导入批次审计” | Should Have | 新增 [INFERRED] | 用户未明确要求“批次管理”，但无此能力无法核对与纠错；需确认 |
| REQ-FUNC-348 | 历史支出写入台账后，系统应当允许业委会成员按任意历史季度或年度生成报表；报表明细应包含历史支出记录，且现有报表查看范围不变（所有登录用户可查看已生成报表） | 用户目标：“生成 2022Q3～2026Q3 往年报表” | Must Have | 新增 | 复用现有报表生成口径与报表页面，不新增统计规则 |
| REQ-FUNC-349 | 历史支出导入、模板下载、批次与明细、整批作废仅允许现任业委会成员（主任、副主任、委员）操作；业主代表、产权业主/户主、同住人、游客、后台管理员均不可导入或查看批次管理页 | 方案A 推荐权限；与收入表一致 | Must Have | 新增 | 后台管理员的“财务”页不含本功能 |
| REQ-FUNC-350 | 系统应当允许有权限的用户对某个历史支出导入批次执行“整批作废”：作废该批次写入的全部台账明细、把受影响的已生成报表标记为过期，并记录操作人、时间、原因；作废后允许重新导入同一批数据 | 方案A 的数据可信与纠错需要 | Should Have | 新增 [INFERRED] | 用户尚未明确纠错方式；无逐行编辑，建议以整批作废替代 |

## 非功能需求

| ID | 描述 | 来源 | 优先级 | 增量类型 | 度量 |
|---|---|---|---|---|---|
| REQ-NFUNC-073 | 历史支出导入的每一次操作都应可审计：至少记录操作人、时间、文件名、批次号、总行/成功/跳过/失败行数、金额合计、作废原因；审计中不得写入完整个人手机号、身份证号或凭据 | 方案A：“保留操作人/时间/导入批次审计” | Should Have | 新增 | 每次导入/作废均产生 1 条审计记录；审计详情不含凭据与完整手机号 |

## 约束

| ID | 约束 | 来源 |
|---|---|---|
| C-377 | “历史支出导入”只用于系统上线前的历史数据补录；上线后新发生的支出仍必须走报销/备用金审批流程。两个入口在页面上须有明确说明 | 用户方案A 与现有报销流程边界 |
| C-378 | 历史支出不得创建报销/备用金/核销申请，也不得创建审批实例；不得出现在“报销/备用金”列表与审批待办中 | 方案A 的隔离要求；现有报销审批流程的边界（`backend/apps/claims/services.py:10-27`） |
| C-379 | 导入后的历史支出明细不提供逐行编辑或逐行删除；纠错方式为整批作废后重新导入（见 REQ-FUNC-350） | [INFERRED] 推荐；待用户确认 |
| C-380 | 模板列顺序固定为：日期、金额、支出类别、用途/事由、备注；CSV 使用 UTF-8，xlsx 只读第一个工作表；日期格式 `YYYY-MM-DD`，兼容 `YYYY/MM/DD` | 方案A 模板要求；收入表导入先例 |
| C-381 | 金额精度为两位小数，单笔金额不得超过系统当前金额上限；金额 ≤0 或超过上限一律拒绝该行 | 现有报销/收入金额规则 |
| C-382 | 单批次 ≤5000 行、文件 ≤5MB；导入失败或中断时不得留下“只有部分行写入”的半批数据 | 方案A 实现约束；数据一致性要求 |
| C-383 | 权限判定以“当前有效的主任/副主任/委员席位”为准；仅有业主代表席位或已失效席位不算有权限 | 方案A 权限推荐；现有业委会成员判定口径 |

## 超出范围（Won't Have）

- 本期不支持在导入文件中携带凭证附件，也不提供导入后批量上传凭证；凭证需求留在开放问题。
- 本期不把历史支出转换成报销单、不生成审批实例、不进入“待我审批”。
- 本期不提供按科目字典强制的“支出类别”枚举；类别按文本填写（如需固定字典另立需求）。
- 本期不实现历史数据的逐行修改/删除；纠错以整批作废后重导为准。
